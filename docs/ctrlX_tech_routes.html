§2 路线①:CpStudio 骨架 + AI MCP进行中 · 主线

定义:用户用 CpStudio V5.11 搭骨架(Station/Module/Command 层级、HMI、handler/变量、库导出、一键生成); AI 经 persistent MCP 完成 IO 配置辅助、PLC 编程(SqM/SqS/自动/手动细节)、编译-修复闭环、下载调试辅助。保留 CpStudio 和 ctrlX。

已实测成果(2026-08-12):persistent MCP 全工具链可用;全工程编译 0 errors / 35 warnings(培训样板固有符号警告); PLC 侧已证明可脱离 CpStudio 运行(库走本地托管仓库自动解析)。

纪律红线:

  • CpStudio 重新生成前必备份 + diff,确认 AI 自定义代码未被覆盖;
  • AI 自定义代码放独立 POU/文件夹并带项目前缀;
  • HMI 符号名骨架阶段定下后,PLC 侧保持不变,避免回炉 CpStudio。

定位:现在的生产路线(OpCon 标准交付 + 客户认可),持续做,但不再追加平台级投入。

§3 路线②:自研 HMI + ctrlX(去 CpStudio)推荐主攻 · 下一站

定义:C#/Python 开发 Linux HMI 上位机,PLC 侧仍用 ctrlX + MCP 流水线;CpStudio 彻底退场。 这是路线① 的自然升级:同一台 ctrlX、同一条 MCP PLC 流水线,只把 CpStudio 承担的 HMI/骨架职能换成自研。

3.1 HMI 与 ctrlX App 的关系(已查证)

  • ctrlX 上的 App 就是 snap 包;ctrlX CORE 2VRS 起还支持 Container Engine App(Docker 镜像装应用);
  • 官方 SDK 支持语言:C/C++、Python、.NET(自包含)、Go、Java、Node-RED、shell;
  • 打包:ctrlX WORKS 内置 App Build Environment;Windows 上可用 Docker 容器跑 snapcraft 构建(见 §6.2);
  • 数据通道:ctrlX Data Layer(设备内直连,Python/.NET/C++ 绑定)+ 内置 OPC UA Server(对外标准通道)。

3.2 两种部署形态

形态做法适用
A. HMI 做成 ctrlX AppWeb 服务打包成 snap/docker 装进 ctrlX,经 Data Layer/OPC UA 本地读写,浏览器/壳显示单机小屏、一体机、随机发货
B. HMI 独立跑在 IPC/屏普通 Linux web/桌面程序,经 OPC UA/MQTT 连 ctrlX大屏、多机线集中监控、上位机与控制器分离

策略:先走 B 的技术、需要时封装成 A。OPC UA 是 ctrlX 现成配好的通道(Symbolconfiguration 导出就是干这个的), HMI 侧零特殊依赖;同一套代码要随设备走时再打成 App。

3.3 HMI 前端选型:原生壳主力,网页备选(已定)

浏览器直接当上位机存在"能被关掉/会卡/观感不专业"的问题,对策与行业实践见 §6.3。结论架构:

同一套后端(C#/Python + OPC UA ↔ ctrlX PLC)
├── 主画面:本机工控屏 → Avalonia 原生程序(.NET 跨平台 XAML)或 Chromium Kiosk
│            全屏无边框,观感 = 传统上位机,操作员无法关闭
└── 备选/远程:浏览器 Web 版 → 工程师笔记本/手机远程监控调试(免装客户端,增值功能)
  • 主画面首选 C# Avalonia UI:AI 生成质量高、无浏览器依赖、Linux 原生运行;
  • Kiosk 模式(Chromium 全屏+无地址栏+systemd watchdog 自动拉起)作为轻量替代;
  • HMI 卡死 ≠ 机器失控:PLC 逻辑在 ctrlX 独立运行,心跳断线自动重连。

  • 沉淀 hmi-framework 仓库:后端服务 + Avalonia 壳 + Web 版 + 报警/配方/权限骨架

4.1 部署平台:Windows 还是 Linux?(已查证)

4.4 独特价值与注意点

  • AI 流水线可能更顺:标准 CODESYS 的 ScriptEngine 完整,ctrlX 贴牌特有的 headless 退出缺陷/CRLF 补丁等坑大概率消失——值得装标准版实测 MCP;
  • 硬件自由:任意 x86 工控机,供应链不受 Bosch 约束;
  • OpCon 库版权属 Bosch:技术上是标准 CODESYS 库可编译,商用前需确认授权范围;
  • 单站授权 = 每台设备持续成本;Linux 运行时先核对内核兼容列表。

§5 路线④:PREEMPT_RT + isolated core + IgH + 自写状态机远期储备

定义:C#/Python 做 Linux HMI;需要硬实时时用 PREEMPT_RT + isolated core 跑 IgH EtherCAT master 作 IO task, 再在 isolated core 跑 cycle task(状态机)模拟 PLC 逻辑。去 CpStudio、去 ctrlX、去 CODESYS。

5.1 可行性与成熟参考

  • 架构完全成立:Intel ECI(Edge Controls for Industrial)参考设计就是这套(PREEMPT_RT + CPU 隔离 + IgH + RT 周期任务);LinuxCNC 同族;
  • PREEMPT_RT 自 Linux 6.12(2024-12)已并入主线,不再需要维护外部补丁;
  • IgH EtherCAT Master:GPLv2 免费;商业闭源分发有合规顾虑时可向 rt-labs 购买商业授权。

5.2 工作量警示(为什么不是主攻)

§6 关键技术细节 Q&A(讨论沉淀)

6.1 snap 包是什么?

snap 是 Ubuntu(Canonical)的应用打包格式:把程序 + 全部运行库依赖打成一个自包含包,运行时沙箱隔离 (默认只能访问自己的目录;要网络/硬件/其他目录需在 manifest 里声明 interface 授权)。 ctrlX OS 基于 Linux,直接采用 snap 作为 App 格式——ctrlX 上的 PLC 运行时、OPC UA Server、Node-RED 等每个 App 都是一个 snap。 好处:依赖不冲突、可签名、可 OTA 升级、可从 ctrlX OS Store 安装或私有侧载。 开发 ctrlX App 时写的 snapcraft.yaml 就是声明包的服务、权限和依赖。

6.2 "用 Docker 构建 snap"是什么意思?

snap 包必须用 snapcraft 在 Ubuntu 环境里构建,但工程师的开发机通常是 Windows。 解决办法:在 Docker 容器里跑 snapcraft——Windows 上执行 docker run -v ${PWD}:/build snapcraft/snapcraft snapcraft, 容器内是标准 Ubuntu,构建完把 .snap 产物吐回 Windows,再装到 ctrlX。 即:Docker 只是构建环境,不是运行环境;App 在 ctrlX 上仍以 snap 形式运行。 (另一回事:ctrlX CORE 2VRS+ 的 Container Engine App 才允许把 Docker 镜像直接作为 App 运行。)

6.3 浏览器做上位机靠谱吗?——行业实践 + 工程解法

质疑成立:裸浏览器确实能被关掉、会卡、观感不像上位机。但行业现状:

  • Beckhoff TwinCAT HMI:HTML5,浏览器或原生壳打开;
  • CODESYS WebVisu:浏览器打开;
  • 西门子 Unified 精智面板:内部 web 技术,Sm@rtServer 远程访问也是浏览器;
  • Bosch 自家 Nexeed HMI:web 系。Web HMI 已是主流,不是异类。

工程解法(两条):

  • Kiosk 模式:工控屏上 Chromium/Edge kiosk 启动——全屏、无地址栏、无关闭按钮、开机自启, systemd watchdog 进程死了自动拉起、页面心跳断了自动刷新。操作员看不到"关闭"的机会,观感=传统 HMI;
  • 原生上位机:C# Avalonia UI(.NET 跨平台 XAML,等价 Linux 上的 WPF)或 Qt,全屏无边框, 观感就是传统上位机,AI 写 C#/XAML 非常拿手,且与网页方案共用后端。

关键架构点:PLC 逻辑在 ctrlX 独立运行,HMI 卡死/关闭只是"看不见",机器不会失控;心跳断线自动重连。 最终选型见 §3.3:主画面 = Avalonia 原生壳(或 Kiosk),Web 版做远程备选。
